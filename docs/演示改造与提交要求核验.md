# 演示改造与提交要求核验

核验依据：项目根目录的 XH-202631 比赛方案 PDF，第 5 页“e. 交付物要求”、第 6–8 页评分标准、第 9–10 页提交方式。这里的页码为文件印刷页码。本文用于工程验收，不构成赛事官方认证。

## 1. 对改造方向的判断

增加可视化演示入口是合理的：任务书要求展示中间决策与推理轨迹，“用户体验与易用性”另占 5 分。但美化页面、录制视频、历史轨迹回放都不能单独证明“可运行系统”。本次同时增加主调度器的运行中注入接收通道，形成真实执行与历史证据回放两个明确标识的模式。

此前建议应作如下调整：

| 项目 | 任务书地位 | 采用方式 |
|---|---|---|
| 材料文档 | 明确要求 | 交付技术报告，覆盖架构、动态路由、记忆、端云、伪代码和复杂度 |
| 可部署环境与自主执行 | 明确要求 | 源码、依赖、运行说明、配置模型后可执行的主工作流 |
| 动态扰动与自主恢复 | 明确要求 | 启动预设注入，以及本次新增的 HTTP 运行中注入；恢复由主调度器推进 |
| 中间决策与轨迹 | 明确要求 | 展示实际路由选择、节点尝试、扰动生命周期、产物和验收 |
| 可视化界面 | 评分明确关注 | 新增 `/demo` 评审入口，保留 `/` 专家看板 |
| 视频 / PPT | 所给任务书未明确规定格式、长度 | 推荐辅助材料，不设虚构的“必须 6–8 分钟”等要求 |
| Docker / Windows 启动脚本 | 未明确要求 | 本次提供 Linux/macOS 启动脚本，Docker 可后续补充；不声称已验证 Windows |
| 离线回放 | 辅助证据 | 明示为历史真实运行，不能替代在线自主执行 |
| 正式报名表与命名 | 提交方式明确要求 | 按 PDF 第八条准备审核通过的报名表和盖章材料；主题及压缩包为“学校-姓名-作品名-联系电话” |

## 2. 本次实际改动

### 评审演示页

- 地址 `/demo`，原专家看板为 `/`。
- 六个章节：任务意图、协作规划、节点失效、需求变更、数据异常、可信交付。
- 根据 `run_state.json.events` 顺序投影节点状态，支持播放、暂停、单步、进度拖动、章节定位和倍速。
- SVG 依赖连线、节点状态、节点尝试次数、实际路由执行单元及候选评分查看。
- 三类扰动卡片和完整生命周期，需求改动前后及图版本、原始/异常/恢复哈希有独立证据详情。
- 最终报告与验收结果只有到达运行结束时才显示；中途不会提前显示最终 PASS。
- 真实执行和历史回放明确标识，切换到真实模式时清空历史验收状态。
- 录屏紧凑布局、全屏、手机宽度适配；不依赖外网字体、CDN 或第三方前端运行库。

历史运行仅保存最终图和阶段记录，没有所有时刻的图快照。回放以保存的最终拓扑作为结构参照，节点状态严格依据事件投影，并在页面明确标注。不得把该功能表述为“精确重建任意时刻拓扑”。

### 运行中注入

```text
运行开始 → 前端提交注入 → HTTP 返回 queued
       → run_dir/control/injection_requests.json
       → 调度器在下一业务节点边界读取
       → accepted / rejected 回执
       → triggered → detected（适用时）→ recovery_started → recovered
       → 后续任务执行 → 业务与证据校验 → 最终验收
```

前端不直接修改 RunState，也不改变执行成功标记。HTTP 仅写入独立的进程安全请求队列；主调度器统一负责状态推进、输入副本恢复和证据写入。请求 ID 由服务端生成，注入类型和目标节点受约束，写入口沿用执行口令认证。

交互演示模式及时保存运行事件和节点状态，不等待长程执行窗口结束；普通长程模式保留原有批量落盘策略。任务图采用原子替换，避免界面读到半写入文件。真实执行模式支持刷新页面后重新连接当前任务；服务端串行化启动请求，防止重复点击同时启动两轮任务。

存在交互请求队列的运行，其注入独立审计另检查所有请求是否由调度器实际接收并登记。被拒绝的注入不会被算作恢复成功，也不能借业务运行 PASS 宣称所有扰动都已处理。

注入在节点边界应用，不中断正在进行的模型请求；不具备物理设备断电、任意进程终止或网络分区注入能力。不存在可执行目标时明确拒绝。执行窗口关闭后拒绝新请求；已入队但未消费的末尾请求会进入阻断记录，不能静默计为恢复成功。

三种注入的能力边界：

- 节点失效：调度边界一次性执行失败，随后走真实重试/恢复流程；演示证据不能自动等同于真实设备宕机和异机迁移。
- 需求变更：更新尚未执行节点的描述、非空证据引用判据和图版本，保留已完成工作；“契约已更新”与“最终需求已验收”分开呈现。任意自然语言业务变更并无通用确定性验收器，不宣称已经支持任意需求子图重构。
- 数据异常：只破坏本轮输入副本，通过 SHA256 检测、隔离、恢复后重试；不改原始资料，不等同于所有语义数据异常。

## 3. 运行与录制

离线回放只需 Python 标准库及随包提供的运行证据：

```bash
bash scripts/start_demo.sh --replay
```

在同一台机器浏览器访问 `http://127.0.0.1:8765/demo`。项目运行于远程服务器时，需要将 8765 端口转发到本机。

真实运行先按 `run.md` 安装环境并设置模型环境变量，然后执行：

```bash
conda activate agent
bash scripts/start_demo.sh --live
```

服务会在终端显示执行口令。打开“真实执行”，输入口令并启动差旅审查；任务开始后可提交三类扰动，等待 accepted 回执及自主恢复。口令只在内存和请求头中使用，不应录入视频。视频建议先输入口令再开始录屏。

也可使用 `DEMO_PORT=8766` 选择端口，`DEMO_PYTHON=/absolute/path/to/python` 指定环境解释器。

离线录制建议：选择“三类扰动 · 自主恢复”→ 录屏布局 → 自动播放 → 三个章节分别查看恢复证据 → 可信交付 → 报告与审计。录制中保留“历史真实运行回放”标识。自动播放压缩等待时间，不改变事件顺序。

在真实模型环境中复核 HTTP 全链路（会调用配置的模型并产生正常用量）：

```bash
python utils/verify_live_demo.py --live
```

该工具启动临时本地 HTTP 服务，通过正式接口启动任务，在任务运行后提交三类请求，最后检查主流程及注入审计。它只负责注入和验收，不代替系统恢复。
